# 02. On-disk layout

EmPo keeps everything for a target project in a single `.empo/` directory at the target repo
root. The layout encodes one hard rule: **`generated/` is machine-owned, everything else is
human-owned.** An agent may edit the human-owned files as it learns; it may never hand-edit the
generated ones.

## The `.empo/` directory

```
<target-repo>/
  .empo/
    config.json          layer 4. adapters, roots, bridges, pack selection. Human-owned.
    flows.json           layer 2. the end-user journeys. AI proposes, human owns.
    spines/
      money.json         layer 2. one critical chain. hops, invariants, traps, citations.
      auth.json          (as many spines as the repo warrants; often zero or one)
    conventions.md       layer 3 state. the false-positive register. grows per review.
    generated/
      graph.json         layer 1 output. nodes, edges, flows, test cross-ref, built-against sha.
      packs.lock.json    which pack versions produced this graph, for reproducibility.
    .gitignore           ignores generated/ by default; see "what to commit" below.
  empo.config.json       optional: root-level pointer if .empo/config.json is not wanted inside .empo
  AGENTS.md              host instructions, a managed block, regenerated by `empo update`
  .claude/               the empo-* skills and the hook entries, regenerated by `empo update`
```

`config.json` may live either at `.empo/config.json` or as `empo.config.json` at the repo root.
The root form exists because some teams keep tool config at the top level and treat `.empo/` as
derived state. `empo init` writes the first form, and `empo init --config-at-root` the second. It
does not ask: a command that prompts cannot run in a hook, in CI or under an agent, which is where a
scaffolding command earns its keep, and the answer is one file move afterwards in a directory the
team owns. Both are supported and documented in [03-config-schema](03-config-schema.md). The root
form moves one file and not the directory: `flows.json`, `spines/` and the rest stay under `.empo/`.

## Ownership, file by file

| File | Owner | Who may write it | Regenerated by |
|------|-------|------------------|----------------|
| `config.json` | Human | Human, or `empo init` once | never automatically |
| `flows.json` | Human | Human; agent may **propose** edits via a diff | `empo init` seeds it, then hand-owned |
| `spines/*.json` | Human | Human; agent appends citations/traps as it learns | never wholesale; appended in place |
| `conventions.md` | Shared | Agent appends during review; human prunes | grows monotonically, pruned by hand |
| `generated/graph.json` | Machine | **`empo index` only.** Never an agent, never a human. | `empo index` |
| `generated/packs.lock.json` | Machine | `empo index` only | `empo index` |

`empo init` writes only what is missing. Every file in the table above that it would write and finds
already there is reported `kept` and left byte for byte as it was. That is what makes it safe to
rerun, and it doubles as the repair command for a half-scaffolded repository: run it again and the
missing files appear beside the ones that were already there. It is also why there is deliberately no
`--force`. A config someone tuned, flows someone approved and a register that grew over months of
reviews are human-owned from the moment they exist, and none of them is reproducible from a file
listing.

The reason this rule is not merely advice: an agent that "helpfully" edits `graph.json` produces
an impact answer that looks generated but is invented, which defeats principle 1 entirely. So it is
enforced as well as stated. The `AGENTS.md` block `empo init` writes states it, and the PreToolUse
hook in the generated `.claude/settings.json` denies any Write or Edit whose path resolves under
`.empo/generated/`, with a reason naming `empo index` as the only writer and a reindex as the repair.
The one hole in the enforcement is a machine with no `empo` installed, where every hook fails open;
that is deliberate and [10-distribution](10-distribution.md) explains what it costs.

## What to commit

Recommended default, and what `empo init` writes into `.empo/.gitignore`:

```
# .empo/.gitignore
generated/
```

Commit `config.json`, `flows.json`, `spines/`, and `conventions.md`. These are the curated,
reviewed, human-owned knowledge and they belong in version control so the whole team shares them.

Do **not** commit `generated/`. It is derived, it is large, it changes on every meaningful commit,
and committing it produces noisy diffs and merge conflicts over machine output. Regenerating it is
seconds of local work (`empo index`), and its embedded `built_against` sha tells you if it is
stale. Teams that want CI to have a graph run `empo index` as a CI step rather than commit it.

An alternative some teams prefer: commit everything including `generated/` so a fresh clone can
`empo query` with zero setup. EmPo supports it; the tradeoff (diff noise vs zero-setup) is theirs.
`empo init --commit-generated` writes a `.empo/.gitignore` that ignores nothing and a config whose
`commit` list records the same decision, so the two halves leave `empo init` agreeing. They can drift
afterwards and nothing repairs them, but the drift is no longer silent: `empo doctor` asks git what
it really does with `.empo/generated` and warns when that contradicts the `commit` list
([03-config-schema](03-config-schema.md) for the field, [06-cli](06-cli.md) for when the check stays
quiet). A warning and never an error, because the `.gitignore` is still what git actually obeys and a
record that has gone stale makes no answer wrong. A rerun of `empo init` keeps both files rather than
rewriting either, so editing one half is still a change to the record and not to the behaviour, or
the reverse. A flag again and not a prompt, for the reason above.

## Staleness is a first-class concept

`graph.json` records the commit it was built against (`built_against`). Every `empo query` prints
that sha and how many commits `HEAD` is ahead of it. The SessionStart hook in the generated
`.claude/settings.json` warns when the graph is stale relative to `HEAD` and says nothing when it is
not, which is what keeps the warning worth reading on the session where it does appear. `empo doctor` is the same answer on
demand, for a human or, with `--json`, for whatever else wants it. The contract is unaffected: EmPo
never silently serves a stale answer. It serves the answer and tells you how old the substrate is,
and you decide whether to `empo index` first.

## Nothing here is secret to EmPo itself

`.empo/` contains knowledge about the target project (its flows, its critical chains). That
knowledge is the target team's, and it lives in the target team's repository. **None of it ships
in the EmPo repository.** The EmPo repo ships the engine, the packs, and the discipline, plus
**synthetic** example artifacts under `examples/`. This boundary is absolute and is the subject of
[11-security-boundaries](11-security-boundaries.md).
